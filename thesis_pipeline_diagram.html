Thesis pipeline: from real code to a confirmed-exploit number

Two separate data sources feed the same detect-then-confirm pipeline, and each produces a different kind of result. This is where the current work (fetching real CVEs) sits in the whole picture.

where we're working right now built but not yet run against real data
1

Pull real CVE ground truth ← you are here

fetch_real_cves.py queries GitHub Advisories for real, disclosed pip-package vulnerabilities in your three CWEs and saves the pre-fix vulnerable code.

2

Triage candidates by hand

Skim the saved JSON files, keep the ones that isolate cleanly as a single vulnerable function -- this becomes your held-out test set.

3

Run the pipeline against ground truth

taint_scan.py then the exploit harnesses run against the held-out set, producing a real (non-self-tuned) accuracy number.

4

Mine realistic prompts

Pull real function signatures/docstrings from popular repos, strip the bodies -- these become the prompts for the actual generation experiment.

5

Generate + run the real experiment

Multiple LLMs regenerate the stripped functions; the same pipeline runs against their output, producing per-model vulnerability and confirmed-exploit rates.

6

Write it up

Methodology section leans on steps 1-3 (honest validation); results section is steps 4-5 (the actual finding).
