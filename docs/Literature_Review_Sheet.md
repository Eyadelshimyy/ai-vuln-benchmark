## Main Research Gaps Identified

1. **Main gap — no verification of exploitability.** All three papers stop at detection (generic static analysis in Sabra et al.; 3-tool SAST + CWE-to-CVE historical mapping in LLM-CSEC; dual-judge SAST+LLM in SafeGenBench), but none confirm that a specific flagged vulnerability is actually exploitable in the generated code. LLM-CSEC's CVE mapping argues a CWE class is historically dangerous, not that this exact snippet is. This is the gap my thesis will address: adding an exploit-confirmation stage after detection for a scoped set of CWE categories (e.g., SQL injection, command injection, path traversal).

2. **Detection methods disagree with each other, and none of the three papers treat this as solved.** LLM-CSEC: 3 SAST tools found zero common CWEs. SafeGenBench: SAST and LLM-judge only agreed 61% of the time. Sabra et al. used only one generic tool (SonarQube), the weakest setup of the three. This motivates using multiple detection methods as my own pipeline's first stage, before exploit confirmation.

3. **Vulnerabilities are usually studied as a side-category of broader code quality** (Sabra et al.: only ~2% of all findings were vulnerabilities, buried under bugs/smells) rather than as the primary object of study — a dedicated vulnerability-first benchmark is still comparatively rare.

4. **Security-focused prompting has inconsistent, sometimes counterproductive effects** (LLM-CSEC: "secure assistant" persona sometimes produced more vulnerable code than the plain assistant) — not something my thesis needs to solve, but worth acknowledging as a confound when designing prompts.

5. **Task scope stays single-function/single-file across all three studies** (no multi-file, project-level generation) — a known limitation but out of scope for a bachelor's thesis; worth naming explicitly as a boundary of my own study too.
