# AI-Generated Vulnerability Detection & Exploit-Confirmation Pipeline

Companion code for the bachelor's thesis **"An Empirical Evaluation and
Benchmark of AI-Generated Vulnerabilities in Code"** (Eyad Hassan
Abdelfatah, GIU Cairo, Cybersecurity B.Sc., supervised by Dr. Marwa Zamzam
and Dr. Ahmed Maghawry).

## The gap this project addresses

The literature review behind this thesis (`docs/Literature_Review_Sheet.*`)
covers four recent papers benchmarking security in LLM-generated code
(Sabra et al. 2025; Shahid et al./LLM-CSEC 2025; Li et al./SafeGenBench
2025; Yoo & Kim 2025). All of them stop at **detection**: static analysis,
multi-tool SAST, SAST+LLM-judge, or CWE-to-CVE historical mapping flags
code as "containing a vulnerability pattern." None of them confirm that a
specific flagged snippet is **actually exploitable**.

This matters because detection tools disagree with each other constantly
(LLM-CSEC: three SAST tools found zero common CWEs across their sample;
SafeGenBench: SAST and an LLM judge only agreed 61% of the time), which
means a meaningful fraction of what gets reported as "vulnerabilities
found" in prior benchmarks could be false positives -- patterns that look
dangerous but are not, in that specific piece of code, actually
attackable.

**This project builds and empirically validates a two-stage pipeline**
that adds the missing second stage:

1. **Detection** -- static analysis (Semgrep) flags candidate
   vulnerabilities in LLM-generated code and maps them to a CWE.
2. **Exploit confirmation** -- a scripted proof-of-concept harness
   actually runs the flagged code against a real (sandboxed) environment
   with a crafted malicious input, and checks for an unambiguous,
   mechanically-verifiable side effect that can only occur if the
   vulnerability is real (a leaked password, a file created by an
   injected shell command, a file read from outside its sandboxed
   directory).

Scope, as finalized: **CWE-89 (SQL Injection), CWE-78 (OS Command
Injection), CWE-22 (Path Traversal)**, in **Python and Java**, using code
generated by **GPT, Claude, and one open-source model**.

## Status: pipeline built and self-validated

The full detection -> exploit-confirmation pipeline is implemented and
has been run end-to-end against a hand-built Python ground-truth set (6
known-vulnerable / 6 known-safe samples, 2 per CWE, covering realistic
variation in how an LLM might phrase each vulnerability or its fix):

```
$ python3 scripts/run_calibration.py

file                        cwe      detected   confirmed
-----------------------------------------------------------
safe_1.py                   CWE-89   False      False
safe_2.py                   CWE-89   False      False
vulnerable_1.py             CWE-89   True       True
vulnerable_2.py             CWE-89   True       True
safe_1.py                   CWE-78   False      False
safe_2.py                   CWE-78   True       False   <- detection false positive
vulnerable_1.py             CWE-78   True       True
vulnerable_2.py             CWE-78   True       True
safe_1.py                   CWE-22   False      False
safe_2.py                   CWE-22   True       False   <- detection false positive
vulnerable_1.py             CWE-22   True       True
vulnerable_2.py             CWE-22   True       True
-----------------------------------------------------------

Exploit-confirmation harness accuracy against hand-built ground truth: 12/12 (100.0%)
```

That's the thesis's core claim, demonstrated on real (if small) data
before a single dollar of LLM API budget was spent: **static detection
alone flagged 8/12 samples, but only 6/12 were actually exploitable** --
`cmdi/safe_2.py` and `path_traversal/safe_2.py` were pattern-matched by
Semgrep (an allowlist-validated `shell=True` call; an `os.path.basename`
call that also happens to look like unsafe path joining) despite being
genuinely safe. The exploit-confirmation stage correctly cleared both.
Every vulnerable sample was correctly confirmed, every safe sample was
correctly cleared -- 100% agreement with ground truth, on the exact
question detection-only prior work cannot answer.

## Repository layout

```
prompts/                    JSON prompt sets, one file per CWE, asking
                             for the relevant functionality WITHOUT
                             mentioning security (so results reflect
                             default LLM behavior, not prompted-for care).

generation/generate.py       Calls OpenAI / Anthropic / any OpenAI-
                             compatible open-source endpoint for every
                             prompt, saves each response with a
                             provenance header. Reads API keys from env
                             vars; skips (doesn't crash) any model with
                             no key configured.
generation/samples/          Where generated code lands, organized
                             model/language/prompt_id.

detection/semgrep_rules/     Local, offline Semgrep rules (no network
                             dependency on the Semgrep Registry) for
                             each CWE in scope, Python first.
detection/run_detection.py   Runs the rules against a directory of
                             samples, emits JSON findings tagged by CWE.

exploit_confirmation/        One harness per CWE. Each imports a sample
                             module by a small fixed contract (see each
                             harness's docstring), fires several
                             canonical payloads at it in a sandboxed
                             environment, and reports confirmed_exploitable
                             based on an unambiguous side effect -- never
                             on "the code looks dangerous."

calibration/python_handbuilt/ Hand-built vulnerable/safe pairs per CWE,
                               used to validate the harnesses themselves
                               (ground truth for the pipeline, not for
                               the eventual LLM comparison).
calibration/juliet/          Notes + plan for extending Java calibration
                              with NIST's public-domain Juliet Test Suite
                              (not vendored here -- see that folder's
                              README for the download + integration plan).

scripts/run_calibration.py   Runs detection + confirmation together
                              against the hand-built set and prints the
                              comparison table above.

docs/                         Literature review sheet (xlsx/md/tex/pdf)
                               and the one-page initial plan, carried
                               over from the thesis-planning phase.

results/raw/                  Detection-stage output.
results/confirmed/            Exploit-confirmation-stage output.
```

## Running it

```bash
pip install -r requirements.txt

# 1. Prove the pipeline works against known ground truth (no API keys needed):
python3 scripts/run_calibration.py

# 2. Generate real LLM code (needs at least one of these env vars set):
export OPENAI_API_KEY=...        # for GPT
export ANTHROPIC_API_KEY=...     # for Claude
export OPENSOURCE_BASE_URL=...   # e.g. a Together AI / Groq / local vLLM endpoint
python3 generation/generate.py --all

# 3. Detect candidate vulnerabilities in what was generated:
python3 detection/run_detection.py --dir generation/samples --out results/raw/detection.json

# 4. Confirm which flagged candidates are actually exploitable:
python3 exploit_confirmation/harness_sqli.py --dir generation/samples/openai/python --out results/confirmed/sqli.json
python3 exploit_confirmation/harness_cmdi.py --dir generation/samples/openai/python --out results/confirmed/cmdi.json
python3 exploit_confirmation/harness_path_traversal.py --dir generation/samples/openai/python --out results/confirmed/path_traversal.json
```

Note: the exploit-confirmation harnesses expect each generated sample to
be adapted to a small fixed function contract (documented in each
harness's docstring) so the harness can drive arbitrary code without
per-sample glue -- this mirrors how the prompts are phrased (asking for
a function/route with a specific signature) but LLM output still needs a
thin, mechanical wrapper step before confirmation can run on raw
generations. That wrapper step is the next piece of engineering, along
with the Java/Juliet side described in `calibration/juliet/README.md`.
